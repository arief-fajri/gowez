## 2026-10-03 — SDL3 via purego works; vsync does not block

- **Change:** T0 spike: throwaway program using `Zyko0/go-sdl3` (binsdl + streaming texture + PollEvent loop), run with and without cgo.
- **Observation:** Window opens on darwin/arm64, backend `metal`, `CGO_ENABLED=0` OK, 3193 frames/2s. `renderer.SetVSync(1)` succeeds and `VSync()` reports 1, yet Present never blocks (≈1600 fps unthrottled).
- **Implication:** The app loop owns frame pacing (`frameBudget = 1/60s` in `internal/app`); nothing above `internal/window` may depend on vsync blocking. Recorded as finding F3 in DRR-001; `SetVSync` kept as best-effort.
- **Evidence:** [DRR-001](records/2026-10-03_windowing-purego-sdl3.md)

## 2026-10-03 — go-text shaping: RunEnd is mandatory; size is fixed.I(px)

- **Change:** `internal/text` implementation on `go-text/typesetting` + `go-text/render` + gofont.
- **Observation:** Omitting `Input.RunEnd` silently shapes an empty run (0 glyphs, advance 0 — the probe's first output). `Size: fixed.I(n)` is n pixels: "Hello" @16px = 37.94px, @32px = 75.83px (linear). `HarfbuzzShaper` zero value is usable; LRU cache documented for reuse.
- **Implication:** `Shape` always sets `RunStart/RunEnd`; tests pin width ratio and glyph counts so a regression to empty runs fails loudly.
- **Evidence:** `internal/text/text_test.go`, probe in `/tmp/textprobe`

## 2026-10-03 — image.RGBA is premultiplied; goldens must not cross color models

- **Change:** Software rasterizer fill path and `tests/golden` comparison.
- **Observation:** Storing straight-alpha bytes in `image.RGBA` (an alpha-0.5 rect) made `png.Encode` un-premultiply garbage → golden mismatch `rgba(50,128,102,128)` vs `rgba(51,128,230,128)` at the same pixel. Comparing decoded `color.NRGBA` (golden) against `color.RGBA` (buffer) via `.RGBA()` is lossy for A<255 and produced false failures even after the fill was fixed. Classification: **A — implementation failure** (fill wrote straight alpha into a premultiplied buffer; latent text-over-rect blend bug) plus an incorrect test comparison.
- **Implication:** `fillRect` now premultiplies with integer round-to-nearest (`premul`); golden tests compare **encoded PNG bytes** (both sides through the same encoder); structural alpha assertions live in unit tests (`TestFillRectPremultiplied`). Scenes must paint opaque backgrounds — written into the `window.Present` contract.
- **Evidence:** `internal/render/backend/software/raster.go`, `renderer_test.go`, `tests/golden/golden_test.go`

## 2026-10-03 — SDL/Cocoa needs the OS main thread; go test functions don't run there

- **Change:** `tests/integration` real-window checks.
- **Observation:** `window.New` from a test function failed with `No available video device`; a standalone probe confirmed SDL_Init fails from a worker goroutine and succeeds on the main goroutine with `runtime.LockOSThread()` (also after `m.Run` parks it). go test executes each `Test` in its own goroutine — `TestMain` runs on the main one.
- **Implication:** GUI lifecycle checks live in `TestMain` before `m.Run`; the `-tags integration` flag keeps them out of default runs; `gowez-hello` must call `gowez.Run` straight from `main()`. Documented in the window package and DEVELOPMENT_GUIDE §1/§4.
- **Evidence:** `tests/integration/window_test.go`

## 2026-10-03 — M1 render budget: 4.2 ms/frame at 640×420 (Apple M2)

- **Change:** Micro-benchmarks in `internal/text` and `internal/render/backend/software`.
- **Observation:** `BenchmarkFrame` = 4.23 ms/op (three text runs dominate; `BenchmarkShape` = 3.6 µs for a full sentence, 1.1 µs for a counter string; command recording = 53 ns). Budget at 60 fps = 16.7 ms.

## 2026-10-03 — SIGINT/SIGTERM arrive ignored by the SDL/Cocoa stack; the app must install its own handler

- **Change:** T11 smoke verification of `cmd/gowez-hello`.
- **Observation:** `kill -TERM` and `kill -INT` (with dispositions explicitly reset to `SIG_DFL` in the child via `preexec_fn` before exec) were both ignored — only `SIGKILL` stopped the process. Baseline Go programs respond to these signals, so the ignore originates in SDL3/Cocoa inside the process (inherited-`SIG_IGN` ruled out by the `preexec_fn` test).
- **Classification:** **A — implementation failure.** The design (loop exits on CloseEvent only) was insufficient: no code path existed for signal-driven shutdown, so the runtime inherited an un-killable process — a violation of the spirit of I12/G-REL-04 (predictable shutdown), even though the window-close path itself was correct.
- **Implication:** `app.loop` now installs `signal.Notify(SIGINT, SIGTERM)` (buffered channel, drained each frame → latency ≤ one frame budget, `signal.Stop` on return restores default dispositions). Graceful shutdown shares the CloseEvent path and exits 0. Verified: both signals → clean exit rc=0, empty stderr. Cross-compiles on windows/freebsd (`syscall.SIGTERM` exists there). A `SIG_DFL` reset is done in tests that need to prove handler behavior.
- **Evidence:** `internal/app/lifecycle.go` (loop sigCh), probe: `python3` subprocess with `preexec_fn=SIG_DFL` → post-fix `SIGTERM exited rc=0`, `SIGINT exited rc=0`

## 2026-10-05 — M2 regression: `align-items` shifted the item but not its subtree (button label off-center by 5.5px)

- **Change:** `internal/layout/layout.go` — `shift()` now recurses into `n.Children`; new `TestLayoutFlexAlignShiftSubtree` (`row-center` + `column-center`); golden `tests/golden/testdata/ui.png` regenerated (intentional render change; `rects.png`/`text.png` byte-identical).
- **Observation:** Operator visual check of `cmd/gowez-hello` found the "Apply" label sitting ~5.5px above the button's center. Measured from `ui.png`: button border box `y 87..119` (cy=103 ✓) but text ink `y 92..103` (cy=97.5 ✗), gaps 3.5px top / 12.5px bottom. Cause: `shift()` (called from `flex_layout.go` for `align-items: center|end` and the column cross-axis) moved only the item's own `Boxes`/`Lines`, never its descendants, so children kept their pre-shift positions. `TestLayoutFlexAlign` asserted only the item's box, and the golden pinned the bug.
- **Classification:** **A — implementation failure.** Design (`align-items` relocates a laid-out item) and guard rail (I-fleet determinism) were sound; the implementation was incomplete. Not B/D/E: no design doc change, no forbidden state, no missing metric.
- **Implication:** Post-layout alignment transforms must be subtree-wide whenever they run after layout — a single-node geometry patch silently desynchronizes parent and child. Regression test now asserts descendant boxes *and* text lines in both axes; verified failing without the fix (child Y=12 vs want 75.75) and passing with it. Golden regenerated deliberately: pixel check now shows label cy=103.0 = button cy, gaps 10/10.
- **Evidence:** `internal/layout/layout_test.go` `TestLayoutFlexAlignShiftSubtree` (fails without the fix: child Y=12 vs want 75.75; passes with it), golden [ui.png](../tests/golden/testdata/ui.png) regenerated with pixel measurement (label ink cy=103.0 = button cy, gaps 10/10; pre-fix cy=97.5 vs 103, gaps 3.5/12.5), operator visual confirmation of `cmd/gowez-hello` (2026-10-05)

## 2026-10-07 — M4 gate: goja embeds cleanly, but the UI tree forced an inline IPC mode

- **Change:** Milestone 4 end-to-end — `internal/script` (goja engine per [DRR-004](records/2026-10-07_js-engine-goja.md): bounded `Eval` 2 s / handler 100 ms via `Interrupt`, exception → `*script.Error` with stack, `gowez.invoke/call/on` host surface, sandbox bootstrap deleting the natives), `internal/ipc` (dispatcher: versioning, permission gate deny-by-default, deadlines, panic recovery, `Code*` incl. additive `-32600` in the schema description, **`RegisterInline`**), `internal/api` (registry + `app.getInfo` success-path proof), `observe` (`JSExceptions`, `LastJSEvalDuration`, `LastIPCDuration`), `internal/app` (`newRuntime` + scene JS wiring: `scene-ids.js` prelude, `demoJS`, `ui.setText` as the sole tree-mutation door, listeners → `FireHandler`), experiments [B](experiments/2026-10-07_b_js-handler-exception.md)/[C](experiments/2026-10-07_c_unknown-method.md), new contract [docs/SCRIPT.md](../docs/SCRIPT.md), doc sweep, smoke run (alive 4 s, SIGTERM → rc 0).
- **Observation:** (a) The Phase-1 spike de-risked every goja assumption before implementation (message+stack in `*goja.Exception`; interrupt bounded then `ClearInterrupt` allows reuse; microtasks auto-drain after both `RunString` and `Callable`; `goja.AssertFunction`, not `vm.Call`). (b) goja has **no memory limit API** — `Limits.MemoryBytes != 0` is rejected with an explicit error instead of silently ignored (P4). (c) The scene's `ui.setText` cannot run on the dispatcher's default handler goroutine: `internal/ui/tree.go` documents the tree as single-goroutine, so a background update would race the UI goroutine — solved with `RegisterInline` (caller-goroutine execution, documented no-block O(1) contract, panic recovered) and proven by `TestInlineHandlerBypassesTimeout` (the deliberate contrast with bounded mode). (d) The plan's "regenerate golden ui.png/ui-state.png" step was wrong: goldens pin their own independent scene, not `uiscene.go` — M4 caused zero golden churn (plan assumption, not a failure). (e) Text input/IME, promised for M4 by the M3 record, was consciously deferred to M5 during planning (scope move recorded in DRR-004 §Scope, EVENTS.md §divergences).
- **Classification:** No failing tests needed A–E classification this milestone; (d) is a recorded plan-assumption correction and (e) a documented scope move — neither a guard-rail violation (MVP IN/OUT unchanged: "JS can call explicit Go APIs" is now checked, IME was never an IN item).
- **Implication:** The engine runs on the UI goroutine with hard budgets, so script work competes directly with the frame budget — the `LastJSEvalDuration`/`LastIPCDuration` metrics exist to measure exactly that (P5). `ui.setText` is the only sanctioned tree mutation from JS until the M5 adapter arrives; anything that must block belongs in `Register`, not `RegisterInline`. The additive `-32600` schema-description edit is recorded in the GUARDRAILS changelog (G-IFACE-03) with no version bump. D/E experiments and native-capability boxes stay open for M6.
- **Evidence:** [DRR-004](records/2026-10-07_js-engine-goja.md), [experiment B](experiments/2026-10-07_b_js-handler-exception.md), [experiment C](experiments/2026-10-07_c_unknown-method.md), `internal/script/{engine,bindings,spike}_test.go`, `internal/ipc/dispatcher_test.go`, `internal/app/input_test.go` (`TestSceneJSDrivesStateThroughIPC`, `TestSceneJSHandlerFailureIsObservable`), [CHECKLISTS M4 gate](../docs/CHECKLISTS.md), full battery green (gofmt, vet, test, `-race`, integration, 0 broken links, smoke run rc 0)

## 2026-10-07 — M5 (partial): pipeline, applier, bundle and text input land; reactivity does not, and three defects came out of the tests

- **Change:** Milestone 5, delivered in part. Strategy chosen on evidence, not assertion ([DRR-007](records/2026-10-07_m5-compile-strategy.md), [spike record](experiments/2026-10-07_m5_compile-strategy-spike.md)): Strategy B (own subset compiler over the Svelte AST) after measuring **35** `svelte/internal/client` internals across the 7 dashboard modules against **196** total exports, plus a missing `queueMicrotask` in goja and a sandbox-contract clash with `TestSandboxSurface`. Delivered: `internal/ui/apply.go` (two-phase applier + `Session` for cross-batch identity), `internal/window` text-input events and the `StartTextInput`/`StopTextInput` contract, `internal/ui.EventKind` `TextInput`/`TextEditing`, `Config.UI fs.FS` + the "UI bundle" startup step ([DRR-006](records/2026-10-07_m5-ui-bundle-config.md)), `ui.apply` as the bundle path's single mutation door, `observe` UI-op metrics, the `@gowez/adapter` pipeline with strict + report modes and a generated gap register ([DRR-005](records/2026-10-07_m5-js-toolchain.md)), `examples/gowez-dashboard` slice with a committed `dist/`, and golden `gowez-dashboard.png`.
- **Observation (why M5 is partial):** the golden image shows a mounted, styled Svelte-authored UI — and simultaneously proves `{#if}` renders **both** arms, `{#each}` renders **one** row instead of N, and `$state` writes do not re-render. The walker emits *static structure* for block constructs. Reactivity was designed (full re-render, diffed against the previous node tree by node id, no virtual DOM because Go already owns layout) but not implemented; the first codegen draft was abandoned rather than shipped half-wired. `docs/SVELTE.md` states the limitation per construct and the M5 checklist boxes that must stay unticked.
- **Observation (defects the tests caught, all class A — implementation failure):** (a) `applyOp` rooted a parent that a later op attached, splitting one component across several roots — visible as `<button>` unreachable by hit testing; rooting now happens once, after the whole batch, skipping explicitly detached nodes. (b) `validateOp` required every referenced node to be created *in the same batch*, which made every incremental update a dangling reference — the model was wrong, not the code, so `Session` now carries the id space and listener registry across batches. (c) `appendChild` matching was validated only against ids created in the batch, so a `removeChild` for a pair appended in an *earlier* batch passed validation and failed mid-apply, breaking atomicity (G-DATA-02).
- **Observation (process):** three of the four "verified facts" in the M5 plan were wrong or half-true. esbuild was **absent** from `package-lock.json` — Vite is 8.3.3 and bundles with rolldown — so DRR-005 is a genuine new-dependency decision, not a confirmation. `parse()` does **not** strip TypeScript (only `compile()` does), and `remove_typescript_nodes` is unexported with deep imports blocked, which is why the adapter strips TS itself under a closed shape set. `Eval` takes no per-call timeout; the 2 s budget is `Limits.EvalTimeout` fixed at engine construction. `npm test` did not exist because the root `package.json` had no `scripts` at all.
- **Classification:** (a), (b), (c) are **A — implementation failure**: the design (two-phase validation; node ids stable for a session's lifetime) was sound and the guard rails were never in question; the wiring was not. The plan-fact corrections are recorded, not silently fixed.
- **Implication:** The **CSS parity test is the highest-leverage thing built this milestone.** It runs the real Go parser over 59 property/value pairs and compares verdict-for-verdict with the TypeScript mirror. It immediately found **20 divergences** — the mirror claimed to allow `min-width`, `line-height`, `font-family`, `text-align`, `opacity`, `rgb()`, `margin: auto`, `flex-direction: row-reverse`, and percentage heights, all of which `internal/style` rejects. A mirror that disagrees silently is worse than none: it fails the build for valid CSS or passes invalid CSS to a startup crash. The adapter CLI also had to ship as CommonJS because bundling esbuild into ESM fails on its dynamic `require('fs')`.
- **Evidence:** 125 adapter tests (`packages/adapter/test/` — compile, reject, typescript, bundle, css-parity, gap-report), `internal/ui/apply_test.go` (incl. `TestApplyOpsAtomicRejectsInvalidStream`, `TestSessionUpdatesAcrossBatches`, `TestSessionRejectedBatchKeepsState`), `internal/app/bundle_test.go` + `input_text_test.go`, `tests/golden/bundle_test.go` + [gowez-dashboard.png](../tests/golden/testdata/gowez-dashboard.png), [docs/SVELTE.md](../docs/SVELTE.md) §Reactivity status, full battery green (`gofmt`, `go vet`, `go test ./... -count=1`, adapter `vitest run`)

## 2026-10-08 — M5 gate closed: reactivity needed a compile backend, not just a runtime

- **Change:** Closed the M5 gate. The missing piece from the previous entry was reactivity, and the fix was not a runtime tweak — it was a **code generator**. The adapter now compiles each module's template into a JavaScript render function (`codegen.ts`) rather than emitting a static op list; the runtime (`runtime.ts`) re-renders on a state write and diffs the fresh node tree against the mounted one, submitting only the difference through `ui.apply`. Also: `ui.Event` gained `Text`/`TextStart`/`TextLength`, text events now dispatch to the **focused** node through `Tree.TextInput`/`Tree.TextEditing` rather than mutating the value mirror in the runtime, and `internal/ui.Session` learned a durable parent map so `removeChild` can refer to a relationship an earlier batch created.
- **Observation (the defect that shaped the design):** the first working version re-rendered correctly once and then went dead. Every `setText` after the *second* interaction carried `nodeId: 0`. The cause: the fresh tree's nodes never inherited the mounted tree's runtime ids, so after the first flush the new tree carried `__id: 0` and the next diff had nothing to write to. It reads as a one-line fix (`next.__id = prev.__id`) but it is a rule worth stating: **a diff must transfer identity from the old tree to the new one**, or the model only works for one render. The same class of bug appeared twice more — state cells were declared *inside* the render body, so every re-render rebuilt them at their initial value and the diff correctly concluded "no change"; and `__flatten` hoisted fragment children into the parent list, shifting every following sibling when an `{#if}` swapped a branch for an empty fragment.
- **Observation (Go side, one class A):** `applyOps` validated `removeChild` against the parent map projected from the *current* batch, so a keyed list update — which removes a node attached by the mount batch — was rejected as "not a child … in this batch". The atomicity guarantee was right; the *scope* of the check was wrong. A node's parent is durable session state, so `Session` now carries it and validation consults the projected map seeded from the durable one. Wrong-but-safe is still wrong: the batch was atomic, it just rejected legal input.
- **Observation (verification, not just shipping):** the first draft of the reactivity test copied the runtime prelude into the test fixture. That would have proved only that a copy works. The tests were rewritten to drive the **committed slice bundle** — the artifact the adapter actually produced — through the real path. A test that duplicates the thing it tests is the JS-side twin of a silent misrender.
- **Classification:** the id-inheritance, cell-scope and flatten bugs are **A — implementation failure** (the model was chosen and documented; the wiring was wrong). The `removeChild` scope bug is also **A**: the design invariant (validate before mutate) was sound and correctly implemented, just against too narrow an input set. None were **B** (the design held up under every test) or **C** (no forbidden state was reached — every failure was a rejected batch with a `-32602` and a `Diagnostic{Component:"ui"}`, which is exactly the behavior I1 requires).
- **Implication:** the re-render model trades *render* cost for *instruction* minimality — one state write re-runs the component and the diff keeps the op count small, but there is no dependency tracking, so any write re-renders everything that reads the cell. For a runtime this size that is the right trade; it is a trade, and both halves are documented in SVELTE.md §Reactivity model rather than left for a user to discover. The `{#key}` directive is a **documented no-op**: it is a remount hint in Svelte, and faking remount semantics would have been worse than saying so.
- **Evidence:** 125 adapter tests (`packages/adapter/test/`), `internal/app/reactivity_test.go` (six tests, driving the committed bundle), `internal/ui/apply_test.go` (`TestSessionUpdatesAcrossBatches`, `TestSessionRejectedBatchKeepsState`), `internal/app/{bundle,input_text}_test.go`, `tests/golden/bundle_test.go` + [gowez-dashboard.png](../tests/golden/testdata/gowez-dashboard.png), [SVELTE.md](../docs/SVELTE.md) §Reactivity model, [CHECKLISTS](../docs/CHECKLISTS.md) M5 gate, full battery green: `npm test`, `npm run typecheck -w @gowez/adapter`, `go build`, `gofmt` empty, `go vet`, `go test ./... -count=1`, `-race`, `go test -tags integration`

## 2026-10-08 — A second window exposed a latent windowing defect: SDL3 was being loaded twice

- **Change:** Added the missing platform proof for M5. `tests/integration/dashboard_test.go` mounts the **committed slice bundle** into a real OS window via `app.Run`, using an `autoCloseWindow` decorator that wraps the real SDL window and injects a `CloseEvent` after three presented frames — so the run is deterministic and finishes in ~0.4 s. `TestMain` (the only one Go allows per package) now sequences two GUI checks and surfaces each as a declarative test: `TestWindowLifecycle` (raw backend) and `TestDashboardWindowMounts` (full bundle path). Also: `examples/gowez-dashboard` gained a `-dist` flag, and DEVELOPMENT_GUIDE §1 documents the manual window check.
- **Observation (the defect the new test found):** the first run of the two-window suite printed a wall of `objc[…]: Class SDL3Window is implemented in both …/libSDL3.dylib and …/libSDL3.dylib … This may cause spurious casting failures and mysterious crashes.` Reading `binsdl.Load()` explains it: it writes the embedded library into a **fresh temp directory** and `dlopen`s it, and `sdlWindow.Close()` called `lib.Unload()`. So the library lifetime was *per window*. Nothing had ever created two windows in one process, so the bug was latent — and Apple's warning names a real failure mode, not a cosmetic one. Fixed by making the library process-scoped (`loadProcessLib`, a `sync.Once`) while window-scoped resources (texture, renderer, window, video init) still release in `Close`, which is what invariant I12 is actually about. The warnings went from ~20 lines to zero, and a later window is no longer handed a closed library.
- **Classification:** **B — design failure.** The implementation faithfully loaded and unloaded the library with the window; what was wrong was the design's unstated assumption that a process has at most one window. Nothing in the `Window` contract, in `Close`, or in the docs said so, so a reasonable second window silently entered a forbidden state. This is the mirror image of the Phase 0 spike lesson: there, a finding count of zero was a bug report; here, a passing test with stderr noise was a defect report.
- **Observation (test design):** asserting a real window without a new exported API took two existing seams — `app.NewWindow` (inject the decorator) and `app.NewReporter` (capture diagnostics) — plus the fact that a failed mount is already a hard startup error, so a nil return from `app.Run` proves manifest + CSS + eval + `ui.apply` all succeeded. `app.Run` never returns its `*App`, so `FrameCount`/`UIOpsApplied` are unreachable after a run; the decorator counts presents instead and the reporter surfaces rejected batches. That is why this needed no change to the public surface.
- **Observation (the example's own instructions were wrong):** `main.go` documented `os.DirFS` as "relative to this source file so the sample runs from anywhere". It is relative to the **process working directory**, so `go run ./examples/gowez-dashboard` from the repo root failed while the comment promised it would work. Verified and fixed with a `-dist` flag and an error that names both working invocations — a false claim in a doc comment is the same defect class as a false claim in a README: it sends the next person down a dead end.
- **Implication:** one window per *run* is still the contract — `sdl.Quit()` in `Close` is not refcounted, so two *simultaneously open* windows would still fight over SDL video init. The fix makes sequential windows safe, which is what any test suite or single-window app needs. Making concurrent windows correct is a separate change and is not claimed here.
- **Evidence:** [`dashboard_test.go`](../tests/integration/dashboard_test.go), [`window_test.go`](../tests/integration/window_test.go) (single-`TestMain` sequencing), [`sdl.go`](../internal/window/sdl.go) (`loadProcessLib`, process-scoped library), [`main.go`](../examples/gowez-dashboard/main.go) (`-dist`), [DEVELOPMENT_GUIDE.md](../DEVELOPMENT_GUIDE.md) §Manual window check, `go test -tags integration ./tests/integration/ -v` green (3 frames presented, zero `objc` duplicate-class warnings)

## 2026-10-08 — Component styles were never scoped: a screenshot review found a leak that grew with app size, and a combinator bug hiding behind it

- **Change:** Closed the M5 gate properly after a visual triage of the slice against the dashboard. Two defects, both in the adapter, both found by looking at the rendered image rather than by a failing test. (a) **Component style scoping:** each module's `<style>` now gets a scope class derived from its path (`src/UserList.svelte` → `s-UserList`), appended to the **last compound** of every selector and to the `class` of **every** element the module renders. (b) **Selector/combinator reporting:** unsupported pseudo-classes, pseudo-elements and non-descendant combinators are now named in a new `CSS-SELECTOR` finding instead of being reported as "selector could not be printed" (`CSS-UNKNOWN`). Also `ui.Node.HasClass` (token-wise class matching, mirroring `internal/style`), the sample shell colour moved off the runtime backdrop so the panel's bounds are visible, and the golden comment + DEVELOPMENT_GUIDE manual check rewritten to separate *pipeline* evidence from *layout fidelity*.
- **Observation (the leak):** measuring the dashboard's stylesheet found **8 selectors declared by more than one module** — `.search` in three, `.bar` and `.nav-item` in two each, plus `.icon-btn`, `.activityli`, `.recentli`, `.insightsli`, `.danger-zone`. The slice had exactly one duplicate, which is why it looked fine; the dashboard had eight. Because `internal/style` matches a class by token and cascade order decides the winner, **the last module's rule silently won for every element in the app**. Verified end-to-end through `internal/style`: with the scope removed, all three `UserList` buttons resolve to App's `padding: 6px 10px` instead of their own `4px 8px`. After scoping, 0 author selectors resolve to more than one rule, and 72/72 rules carry a scope.
- **Observation (the bug behind the bug):** writing the combinator test exposed that descendant selectors were compiling to the literal text `[object Object]`. `rel.combinator` is an AST **node**, and the printer coerced it with `String()`. With `parse({modern: true})` the operator is the combinator's `name` (`' '`, `'>'`, `'+'`, `'~'`); `type` is always the string `"Combinator"`. Every descendant rule in every component was therefore emitting a selector Go cannot match and dropping the rule **without a finding**. This had been latent because nothing in the suite used a descendant selector.
- **Classification:** (a) and (b) are both **A — implementation failure.** The design was never in question: `internal/style` already accepted several classes on one compound, so scoping needed no engine change and no `protocol/` or root-API touch (Level A). The wiring did not exist. It is *not* B, because scoping was never a design decision — it was an omission, and the gap register never mentioned it because the gap register only counts *rejections*, never *silently wrong output*. That last point is the real lesson.
- **Observation (the golden diff, measured rather than assumed):** the golden PNG changed on 1452 of 576000 pixels (0.25%), confined to the top 160 rows. Rather than regenerate on faith, the button geometry was dumped: `UserList` buttons went from 30.5px to 26.5px tall — exactly the 6px→4px padding difference scoping was supposed to restore — while `App` buttons were unchanged. It is an improvement. The remaining visual overlap between list rows is a *different*, pre-existing gap: `{#each}` rows have no vertical spacing because `margin`/`gap` are outside the subset (M7 work), not something scoping touched.
- **Observation (a test that had to be rewritten):** `textOfClassCount(t, s, "", "button")` used an empty class string as a **wildcard**, relying on `GetAttribute("class") == ""` matching every button that had no class. `HasClass("")` correctly refuses the empty token — matching `""` would match every node in the tree — so the helper had to express the wildcard explicitly (`class == "" || x.HasClass(class)`). The old helper was not testing class matching; it was accidentally testing "has no class", and the scoping work made that visible. Two other helpers were comparing whole class strings and are now token-wise.
- **Implication:** **a gap register that only counts rejections cannot see a silent misrender.** 139 findings were published while eight rules were quietly overriding each other. The countermeasure adopted here is `TestBundleStylesAreScoped`, which asserts the *resolved* value per element through the real stylesheet rather than asserting the CSS text — because the class being present in the text is necessary but not sufficient. The same lesson applies to the golden: it pins the pipeline, so a byte-exact image says nothing about whether the layout is right. Both are now labelled as what they are.
- **Evidence:** [`scoping.test.ts`](../packages/adapter/test/scoping.test.ts) (10 tests: scope on selectors, on every element, per-module isolation, collision detection, combinator + pseudo reporting), [`TestBundleStylesAreScoped`](../tests/golden/bundle_test.go) (verified decisive — fails with `padding = [6 10 6 10], want [4 8 4 8]` when the scopes are stripped from the committed bundle), [`TestHasClass`](../internal/ui/ui_test.go), `npm run report:dashboard` (139 findings, unchanged: the 4 `CSS-UNKNOWN` became 4 honest `CSS-SELECTOR`), leak measurement (8 → 0 author selectors, 72/72 rules scoped), [SVELTE.md](../docs/SVELTE.md) §Component style scoping + §Gap register, [CHECKLISTS](../docs/CHECKLISTS.md) M5 scope note

## 2026-10-08 — M6a: the measuring instrument was broken, and the plan I approved was built on it

- **Change:** M6a — custom properties and `var()` substitution, `color-mix(in srgb, …)`, `list-style: none`, `outline: none`, and per-side border colour (`ComputedStyle.BorderColor` is now `[4]uint32` with `border-color` expanded to four longhands, so `border-bottom: 1px solid red` is expressible). Also fixed the adapter's report mode so the gap register is **complete** instead of one finding per rule.
- **Observation (the instrument, first):** planning M6a against the published baseline of 139 findings, I could not account for `font-family`, `box-shadow`, `grid-template-rows` and `100dvh` — all of which are in the sample. The adapter's `validateCssSubset` **throws on the first bad declaration in a rule**, and report mode caught the throw, so it recorded one finding per *rule*. `.app { display: grid; grid-template-columns: 240px 1fr; height: 100dvh }` reported only `display: grid`. The true baseline was **259**, not 139 (`CSS-PROPERTY` 185, not 65). `cssSubsetErrors` now collects every rejection; strict mode still throws on the first, because that is the one an author needs.
- **Classification:** **D — missing observability.** The runtime never misbehaved; the measurement did, and every milestone gate is read from it. This is the second time the gap register has been the thing that was wrong (the first was scoping, which it could not see because it counts rejections and scoping produced *wrong output* rather than a rejection).
- **Implication:** an under-reporting counter is worse than an inaccurate one, because it is **non-monotonic in the wrong direction**. Closing one property can unmask two others behind it, so the count can stay flat or rise while a milestone makes real progress — and a gate of the form "the count must fall" then fails for correct work. Any instrument that decides whether a milestone succeeded has to be able to see the whole thing first. That is why the corrected gates in DRR-008 are per-step numbers traceable to a named list of properties, not one aggregate target.
- **Observation (the plan I was given was wrong, and measuring said so):** the approved order put the shorthands first and `var()` second. Measuring the sample: **32 of 39** shorthand declarations use `var()` — `background` 23 of 24. `border: 1px solid var(--border)` is not a colour, so the shorthand parser would reject it for the wrong reason and the finding would stay. The shorthands were a large-looking diff producing almost no gate movement. `var()` is the precondition, not an adjacent feature. The order was inverted in the design note before any of it was built.
- **Observation (a bug the parity test could not see, and then could):** the TS mirror's `var()` deferral ran **before** the property-existence check, so it silently accepted `background: var(--x)` and `grid-template-columns: var(--x)` — properties the subset does not have. Go rejects both, so the two implementations disagreed, and the register's shorthand counts collapsed from 35 to 3, which is what exposed it. Every existing parity case used a known property, so the blind spot was exactly the new feature. Fixed the ordering and added `{"background", "var(--accent)", false}` plus two more to `tests/parity`. A mirror that is only compared on cases that already pass is a mirror nobody is really testing.
- **Observation (flaky, which is the informative kind):** `TestCustomPropertyInheritsItsComputedValue` passed on single runs and failed intermittently under `-count`. The cause was real: `--ink: var(--fg)` failed with "not defined" whenever map iteration visited `--ink` before `--fg`, because the resolver substituted against an empty memo instead of resolving references first. Fixed by resolving every reference before substituting. The regression test is a three-link chain run `-count=25`, which makes an order-dependent implementation fail reliably. *I could not demonstrate the failure against the old implementation afterwards: stashing the file also reverted the unrelated per-side border-colour change and the package stopped compiling — so the new test's value rests on the mechanism, not on a recorded before/after.*
- **Implication (one thing the mirror genuinely cannot do):** a well-formed but unresolvable reference — `var(--nope)`, or `var(fg)` with a non-custom-property name — is **not** a build-time finding. Substitution needs the cascade, so it is a resolve-time error (`style: node 1: color: var(--nope) is not defined`). The mirror accepts well-formed `var()` values and only checks that parentheses balance. That is a difference in *reach*, not in verdict, and it is now stated in both the parity test and CSS-SUBSET.md rather than left for someone to discover. An earlier reject-fixture asserted the opposite and was wrong.
- **Implication (colour-mix):** only `in srgb` is accepted, and other spaces are refused **by name**. Mixing in srgb while the author wrote `in oklch` returns a colour that differs from every browser — a silent wrong answer rather than a refusal. Interpolation is premultiplied: `color-mix(in srgb, #f00 50%, transparent)` is `rgba(255,0,0,0.5)`, not `rgba(128,0,0,0.5)`. Three of my own test expectations were wrong here before the maths was right — `black 25% + white` is light grey (0xbf), and `0.5 × 255` rounds to 128, not 127.
- **Gate:** `CSS-PROPERTY` **185 → 123**, total **259 → 197**. Remaining `var()`/`color-mix()` findings: **0**. Golden PNG byte-identical and the slice bundle unchanged — the slice uses no `var()`, which is itself the evidence that this step is additive. 170 adapter tests, 92 parity cases, full battery green.
